# PaySim Digital Forensics Investigation

## Role of Digital Forensics in Banking and Financial Cybercrime Investigation

A research-oriented digital forensics implementation that combines **machine-learning-based financial fraud detection** with **structured forensic case reconstruction, evidence mapping, and traceability analysis** using the PaySim synthetic financial transaction dataset.

The project demonstrates how suspicious financial transactions can be transformed from analytical outputs into structured candidate investigative cases while preserving explicit links between suspicious transactions, evidence records, and investigative findings.

> **Important:** A suspicious transaction generated by the machine-learning model is an **investigation seed**, not proof of criminal activity.

---

## 1. Research Overview

### Research Title

**Role of Digital Forensics in Banking and Financial Cybercrime Investigation**

### Research Question

**How can analytical outputs from financial fraud detection be systematically converted into evidence-linked investigative cases, and how can the completeness and traceability of those cases be evaluated?**

### Research Gap

Existing studies have extensively addressed financial fraud detection, machine learning, explainable artificial intelligence, graph-based fraud analysis, and the application of AI in digital forensics.

However, there is a need for an empirically evaluated and reproducible workflow that explicitly connects:

```text
Fraud Detection
      ↓
Suspicious Transaction
      ↓
Context Reconstruction
      ↓
Forensic Case
      ↓
Evidence Mapping
      ↓
Finding Traceability
```

This project investigates that detection-to-investigation bridge using measurable forensic evaluation criteria.

# 2. Research Objectives

The project has the following objectives:

1. Identify suspicious financial transactions using machine learning.
2. Construct structured investigative cases from suspicious transactions.
3. Incorporate temporal and account-related contextual evidence.
4. Map investigative findings to supporting transaction records.
5. Evaluate structural completeness and evidence traceability.
6. Measure contextual evidence enrichment.
7. Analyze the sensitivity of forensic reconstruction to different temporal windows.

## Step 2 — Preprocessing

The preprocessing stage:

- Preserves the original dataset.
- Creates deterministic transaction IDs.
- Creates original row references.
- Preserves temporal ordering.
- Validates important transaction fields.
- Saves the processed dataset.

Example transaction IDs:

```text
TX00000001
TX00000002
TX00000003
...
```

These identifiers support downstream forensic traceability.

Output:

```text
data/processed/paysim_preprocessed.csv
```

---

## Step 3 — Causal Feature Engineering

The feature engineering stage creates transaction-level and historical behavioural features.

Examples include:

- Log transaction amount
- Square-root transaction amount
- Transaction hour
- Simulation day
- Transaction-type indicators
- Previous origin transaction count
- Previous origin transaction amount
- Previous destination transaction count
- Previous destination transaction amount
- Recent account activity
- Historical transaction behaviour

Historical features are constructed using information available before the current transaction to reduce future-data leakage.

Output:

```text

```

# 6. Leakage-Audited Machine Learning

Two models were evaluated:

1. Logistic Regression
2. Random Forest

A temporal train/validation/test strategy was used rather than a random temporal split.

### Temporal Partition

| Partition | PaySim Steps |
|---|---:|
| Training | 1–323 |
| Validation | 324–399 |
| Test | 400–743 |

### Leakage Controls

The final predictive model excludes:

- Account identifiers
- Raw account balance fields
- Balance-derived predictive features
- Target label
- `isFlaggedFraud`
- Future transactions

The initial balance-derived experiment produced unusually near-perfect results and was therefore rejected in favour of the leakage-audited configuration.

---

# 7. Model Performance

The final audited models were evaluated on the test set at the standard comparison threshold of **0.50**.

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---:|---:|---:|---:|---:|---:|
| Logistic Regression | 82.33% | 3.12% | 91.58% | 6.03% | 0.9426 | 0.2125 |
| Random Forest | 98.30% | 23.87% | 79.82% | 36.75% | 0.9703 | 0.3153 |

The **Random Forest** was selected for the forensic investigation stage because it achieved the stronger overall discrimination and PR-AUC performance.

---

# 8. Forensic Suspicion Threshold

The model-comparison threshold and forensic investigation threshold are intentionally different.

### Model Comparison

```text
Threshold = 0.50
```

This threshold is used for standard model comparison.

### Forensic Investigation

A threshold of:

```text
0.95
```

was selected using validation data by maximizing F1 score and then frozen before evaluation on the test set.

The frozen threshold was used to generate suspicious transaction seeds for forensic reconstruction.

### Test Performance at Forensic Threshold

| Metric | Result |
|---|---:|
| Precision | 68.33% |
| Recall | 8.74% |
| F1-score | 15.50% |
| ROC-AUC | 0.9703 |
| PR-AUC | 0.3153 |
| Suspicious seeds | 480 |

The high threshold prioritizes precision for investigation seed generation rather than maximizing the number of detected transactions.

# 9. Forensic Case Reconstruction

Each suspicious transaction generated by the forensic threshold is treated as an **investigation seed**.

The reconstruction process searches for contextual evidence using:

- Temporal proximity
- Source-account relationships
- Destination-account relationships
- Relevant origin/destination relationships

The final selected reconstruction configuration uses:

```text
Temporal window = ±24 PaySim steps
```

---

# 10. Final Forensic Results

| Metric | Result |
|---|---:|
| Suspicious seeds | 480 |
| Candidate forensic cases | 480 |
| Evidence records | 491 |
| Cases with contextual evidence | 11 |
| Contextual enrichment | 2.29% |
| Structural completeness | 100% |
| Seed traceability | 100% |
| Evidence traceability | 100% |
| Finding traceability | 100% |
| Multi-seed cases | 0 |
| Selected forensic threshold | 0.95 |
| Selected temporal window | ±24 steps |

The 491 evidence records consist of:

```text
480 suspicious seed records
+
11 contextual evidence records
=
491 evidence records
```

All 480 suspicious seeds resulted in structurally complete candidate cases.

However, only 11 cases contained additional contextual transaction evidence.

Therefore:

> **100% structural completeness does not mean that every case contains rich contextual evidence.**

---

# 11. Temporal Window Sensitivity

The reconstruction process was evaluated using four temporal windows while keeping the model and suspicion threshold fixed.

| Window | Contextual Cases | Contextual Enrichment | Avg. Evidence / Case |
|---|---:|---:|---:|
| ±1 step | 2 | 0.42% | 1.0042 |
| ±6 steps | 3 | 0.62% | 1.0063 |
| ±12 steps | 5 | 1.04% | 1.0104 |
| ±24 steps | 11 | 2.29% | 1.0229 |

The **±24-step window** produced the highest contextual enrichment among the tested configurations.

This result should not be interpreted as proof that ±24 steps is universally optimal for real-world financial investigations.

---

# 12. Evidence Traceability

The project evaluates three levels of traceability:

### Seed Traceability

Every candidate case maintains a reference to its suspicious seed transaction.

```text
Case → Suspicious Seed → Transaction ID
```

### Evidence Traceability

Every evidence record is linked to its originating transaction.

```text
Case → Evidence Record → Transaction ID
```

### Finding Traceability

Each case preserves the relationship between the investigative finding and the supporting evidence.

```text
Finding → Evidence → Source Transaction
```

The final implementation achieved:

```text
Seed Traceability       = 100%
Evidence Traceability   = 100%
Finding Traceability    = 100%
```

# 13. Important Research Interpretation

The implementation demonstrates a structured workflow for converting machine-learning outputs into candidate forensic cases.

It does **not** claim that:

- Every suspicious transaction is fraudulent.
- The system proves criminal activity.
- The system identifies criminals.
- PaySim represents complete real-world banking evidence.
- Transaction-only evidence is sufficient for a complete financial crime investigation.
- ±24 steps is universally optimal.

The model provides **investigation seeds**, while the forensic reconstruction layer organizes available transaction evidence around those seeds.

---

# 14. Limitations

### 1. Synthetic Dataset

PaySim is a simulated financial transaction dataset and does not represent the full complexity of real banking systems.

### 2. Limited Forensic Artifacts

The dataset does not contain external forensic evidence such as:

- IP addresses
- Device information
- Authentication logs
- Email records
- CCTV
- Browser information
- Mobile-device evidence
- Bank employee records
- Real-world identity information

Therefore, the reconstruction is limited to available transactional evidence.

### 3. Low Contextual Enrichment

Only:

```text
11 / 480 cases
```

contained additional contextual transaction evidence at the selected ±24-step window.

### 4. No Multi-Seed Cases

No candidate case contained multiple suspicious seeds in the final reconstruction.

### 5. Investigation Seed vs. Proof

The ML model identifies transactions for investigation. It does not establish criminal intent or guilt.

### 6. Temporal Window Limitation

The ±24-step configuration performed best among the tested windows, but this does not establish a universal forensic investigation window.

# 30. Final Note

This project demonstrates an experimental and reproducible approach for connecting machine-learning-based financial fraud detection with structured digital forensic investigation.

The strongest result is not simply the fraud-classification performance. The implementation also evaluates whether suspicious analytical outputs can be converted into **structured, evidence-linked and traceable investigative cases**.

Because PaySim is synthetic and transaction-only, the findings should be interpreted within the limitations of the available dataset and should not be generalized directly to real-world banking investigations without validation using appropriate real-world forensic evidence.
